# Verification Catalog

## Purpose and scope

Validating an implementation means gathering evidence that individual parts work, that they work together, and that users or consumers can accomplish what the spec promises.

This catalog covers testing, review, and analysis methods for any type of software. Select them according to behavior, affected components, and the risk of each increment. **It is neither a checklist to execute in full for every spec nor a guarantee that the software is defect-free.**

## Proportionate selection

1. Review acceptance criteria and risks before writing code. Resolve ambiguities that affect expected outcomes; human review of these scenarios is especially valuable.
2. Choose the simplest check that provides sufficient evidence. One test may cover several criteria. Do not require every testing level for the same behavior.
3. Favor fast tests for rules and boundary cases; use real integrations for changed connections and a small number of complete workflows for essential behavior.
4. Automate repeatable checks that protect lasting behavior. Use manual review for exploratory, visual, or product-level concerns when more appropriate.
5. Add specialized checks when a concrete risk warrants them. Do not introduce tools, services, CI, or infrastructure merely to complete this catalog.

Record selected checks and risk-relevant exclusions only. Distinguish **not applicable** from **required but pending**. Missing tooling does not make a requirement inapplicable.

## Methods and checks

### V01. Requirements and scenarios

Ensure each criterion has an observable outcome: inputs or preconditions, action, expected result, and permitted or prohibited effects. Identify excluded scope and compatibility that must be preserved.

Expected results must come from requirements, reviewed examples, or references independent of the implementation. Code and tests generated by the same agent may share an incorrect interpretation.

### V02. Build and static analysis

Where applicable, run compilation, packaging, type checks, linting, and static analysis on affected components. Verify that the artifact can start or be consumed in the target environment.

These checks detect particular classes of errors; they do not establish behavioral correctness. Reuse the project's configuration and review relevant findings.

### V03. Unit and business-rule tests

Test isolated logic: calculations, validation, transformations, state transitions, and business rules. Cover representative examples, boundaries, and relevant invariants.

Assert observable outcomes and effects. Avoid tests that merely reproduce the implementation or depend unnecessarily on internal details.

### V04. Integration and persistence

When connections between modules, files, databases, processes, or services change, test them in a controlled environment with the necessary real components.

Verify reads and writes, integrity, required transactions or atomicity, and failure handling. When formats or schemas change, test existing data, migrations, and information preservation.

Test doubles can simulate failures or isolate external services; they do not establish that the real integration works. Record what was simulated and the remaining uncertainty.

### V05. Contracts and interfaces

For APIs, CLIs, libraries, events, or interchange formats, verify valid and invalid inputs, outputs, errors, and effects against the contract.

As applicable, check status or exit codes, data structures, consumer compatibility, and the absence of unintended changes when an operation is rejected. Test the interface directly rather than relying solely on a graphical interface.

### V06. User interface and complete workflows

Where a user interface exists, check relevant interactions and states: initial, empty, loading, success, error, and retry. Review accessibility and adaptation to devices when required.

Verify the increment's main workflow with the necessary real components through automated end-to-end tests or reproducible manual checks. This may involve a graphical interaction, a command, or a library consumer.

Product review also assesses whether the workflow makes sense and meets the underlying need. A successful demonstration does not replace error cases or regression testing.

### V07. Errors, boundaries, and concurrency

Select cases according to risk: empty, duplicate, or extreme inputs; repeated operations; network, file, or persistence failures; interruptions or restarts; older data; and concurrent operations.

Define the expected behavior first: cancellation, partial preservation, retry, idempotency, or recovery. Verify that data loss, duplication, or inconsistent states do not violate the spec. Avoid hypothetical combinations unrelated to the change.

### V08. Security and data protection

For applicable controls, test both allowed and prohibited operations. For example, a user must not access another user's private data through a direct request, even if they know its identifier.

Verify controls in the component that actually enforces them; hiding buttons does not establish authorization. Select tests for input validation, isolation, data exposure, and other applicable requirements.

Where appropriate, scan for vulnerable dependencies, accidentally committed secrets, and security issues in code. Review and address findings according to risk. Scanners complement behavioral tests and design review; they do not certify security.

### V09. Regression

Run existing tests for affected behavior and its dependencies. Expand to the full suite when scope, risk, or low execution cost justifies it.

Where feasible, accompany a defect fix with a test that reproduces the defect and guards against recurrence. Regression testing reuses existing tests; it does not require a duplicate suite.

### V10. Test quality

Check that:

- Assertions verify meaningful outcomes and side effects.
- Expected results are not calculated by repeating the logic under test.
- Mocks do not replace the connection the test claims to verify.
- Tests are not deleted, weakened, or disabled merely to obtain a passing result; justified changes to expectations are explained.
- Intended tests are discovered and executed, distinguishing failed, skipped, and flaky tests.
- Test data, time, and randomness are controlled when they could make results irreproducible.

Coverage helps identify unexecuted code; it does not establish test quality. For complex or critical rules, consider property-based testing or mutation testing when they add value. Do not require them by default.

### V11. Risk-based change review

Review what changed, where, why, and how it was checked. Focus human review on permissions, sensitive data, destructive operations, migrations, core rules, new dependencies, architecture, and changes to tests or CI.

Review depth depends on risk and may require detailed code inspection or specialist support. A second AI review is supplementary and may share errors with the implementing agent.

### V12. Reproducible execution and CI

Run checks against the version intended for integration or delivery. Record the code revision or working-tree state, commands, environment, and results. Rerun affected checks if the code changes afterward.

Use isolated test data and reproducible setup. Do not run destructive tests against real user or production data.

CI automates these same checks when adopted; it is neither a separate test type nor a prerequisite for starting every project. Where CI exists, failed mandatory checks must block integration. Review changes to that configuration and retain accessible results. An agent's claim does not replace tool output.

### V13. Performance, compatibility, and operation

Apply when justified by the change or requirements:

- **Performance:** measure latency, resource consumption, or capacity using defined workloads and thresholds, without inventing arbitrary targets.
- **Compatibility:** test supported platforms, versions, devices, or formats.
- **Delivery:** verify installation, upgrades, startup or deployment, and a basic workflow in the target environment.
- **Diagnostics and recovery:** verify useful logs that do not expose sensitive data, and procedures to recover the service or data. If recovery depends on backups, test restoration.

Rolling back code does not necessarily roll back data or migrations. Schedule checks that require the released environment for that stage and distinguish them from pre-release validation.

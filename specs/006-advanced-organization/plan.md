### 3.1 Trusted persistence contract

Add `archived_at timestamptz null` to `public.lists`; `NULL` means Active. Existing rows need no data rewrite. The list collection queries filter by authenticated owner and archive state. The current owner/name unique constraint continues to reserve names across both Active and Archived lists.

Every list mutation derives the owner from `auth.uid()`, locks the owner profile row to serialize list-count changes, then locks the parent list before touching dependent records. Validate and normalize names at the trusted boundary using the existing 1–80-character and owner/name uniqueness rules. Keep the 100 active-list limit from spec 001; archived lists do not count as active. Restore rejects at the cap without changing the archived row or its data, and the client reports a localized limit state. This behavior is confirmed in FR-04/AC-04.

Duplicate runs in one transaction: create a new list identity/name, copy only non-deleted concepts in stable source position order with fresh concept IDs and pending state, and copy no rounds, appearances, practices, notes, or operation receipts. The source is unchanged. Reject duplicate names/limit/ownership errors without partial copy. FR-03 permits duplicating an archived source; expose that list-level create action from its Archived card menu, while the archived detail itself remains read-only.

Archive/restore only updates the archive marker and list timestamp; it preserves concepts and every history record. Archive, restore, duplicate, rename, and delete must serialize against round/concept/practice mutations by locking the same parent list first. Permanent delete uses the existing anonymization trigger and foreign-key cascades; the new RPC is the only client-accessible list deletion path. The trigger behavior is not reimplemented in the new RPC.

The active-list guard must cover all trusted list-linked writes, not only visible buttons: list rename/content changes as applicable; concept create/batch/update/delete; round mark/return/draw/new-round; associated practice save; and associated practice-note update/delete. Archived read APIs remain available. `get_or_create_current_round` cannot be used to open an archived list because it mutates by creating a round; provide/use an owner-checked read-only current-round path that returns no round when none exists. Independent practice/note rules remain unchanged.

Bulk work reuses the existing per-item contracts and round operation ledger. Execute per-item operations sequentially so the current per-list recovery envelope cannot be overwritten by concurrent round actions. Continue after definitive item-level rejections, report each result, and retry only failed items after rechecking ownership/current state. If an operation is unresolved because its response is ambiguous, reconcile through its existing operation ID before continuing; do not mark unattempted items as successful or repeat an applied appearance. No larger batch service or new transaction boundary is introduced unless the focused integration evidence shows the existing contracts cannot satisfy FR-08.

### 3.2 Search and bounded queries

`docs/global-plan.md` and spec 001 cap active lists at 100, but archiving can make the archived collection exceed that count. Do not fetch/render all archived lists or all concept rows merely to filter them. Use owner-filtered, keyset-paginated list queries with allowlisted sort values and stable identity tie-breaks. Search uses the clarified trimmed, partial, case/diacritic-insensitive name match, scoped to the selected collection. Keep query text and sort state in the current view; do not add account preferences or URLs.

To satisfy diacritic-insensitive substring matching in SQL without downloading the entire archived collection, use PostgreSQL `unaccent` for a trusted normalized search key and `pg_trgm` for a trigram search index, subject to local Supabase migration verification. Supabase/PostgreSQL 17 documentation lists these extensions and their intended functions; consult the [PostgreSQL 17 `unaccent` module](https://www.postgresql.org/docs/17/unaccent.html), [PostgreSQL 17 `pg_trgm` indexes](https://www.postgresql.org/docs/17/pgtrgm.html), and [Supabase database extensions guide](https://supabase.com/docs/guides/database/extensions) (consulted 2026-11-19). Store/recompute the search key in the trusted write path; never accept a client-supplied normalized key as authority. Keep sort fields allowlisted, not interpolated user SQL.

**T01/T02 local feasibility evidence (2026-11-19):** Configured Supabase runs PostgreSQL 17.11; `unaccent` 1.1 and `pg_trgm` 1.6 are available. A synthetic private-schema probe with 1,000 archived names plus active controls confirmed accent/case-insensitive partial matching, collection isolation, deterministic ties, and two keyset pages of 100 with no overlap. With a trigram GIN index, a five-character substring used a bitmap index scan. One-character search has no usable trigram and used a sequential scan across 1,002 rows; the rare-match ordered query took about 0.56 ms in the first local run. This is evidence for the specified Q04 fixture, not a latency guarantee or a cap on archived data. A synthetic 1,000-concept state-filter/order query used the proposed `(list_id, state, position, id)` B-tree and returned 100 ordered pending rows. Probe schema, rows, and temporarily installed extensions were removed after T01.

T02 applied `20261121150000_vs06_list_collection_search.sql` to local Supabase and verified `unaccent`-derived keys, accent/case-insensitive search, escaped `%`/`_` and SQL punctuation as literal input, owner/collection isolation, the five allowlisted orders and their keyset cursors, and bounded pages against 1,000 archived fixture rows. The existing `create_private_list` path derives `name_search_key` through the trusted trigger. Service tests verify the typed RPC argument mapping and lookahead cursor. The migration and checks do not implement rename/duplicate key maintenance, archive mutations/guards, or production behavior; those remain later tasks. Keep full substring semantics and revisit index strategy if the representative workload changes.

List Detail filters should be pushed into the owner/list-scoped concept query and preserve existing stable `position, id` order; use the current round state and exclude soft-deleted concepts. Because there is no total concept-count cap, use a bounded page/continuation strategy within the existing scroll treatment if workload evidence requires it; selection applies only to loaded filtered results and retains selected IDs while the filter remains unchanged. Do not add a new user-visible selection cap without a spec change. Measure a synthetic workload of up to 1,000 archived lists and 1,000 concepts in one list as a Q04 review fixture, not as product limits or a latency promise. If query/index evidence shows the selected indexes do not support the target operations, revise the plan before dependent implementation proceeds.

## 5. Failure, retry, and concurrency behavior

- **Duplicate/rename:** validate in the interface for feedback and again in the RPC. Database uniqueness is authoritative. On duplicate name, show the localized field error and leave existing rows unchanged.
- **Archive/restore:** show success only after the RPC confirms. Retry/reconciliation must not create another transition. At 100 active lists, reject restore and leave the archived row and contents intact; show the localized instruction to free a slot first.
- **Duplicate:** atomic copy; after timeout, reconcile by the operation identity or request fingerprint so retry cannot create a second copy. If existing RPC design cannot distinguish an intentional second copy from retry, add a text-free operation receipt bound to owner, source, and requested name; do not infer success from name alone.
- **Delete list:** explicit confirmation offers Archive instead. Archive option calls only archive RPC. Confirmed delete uses the current trigger/cascade. Unresolved result must be reconciled by re-reading owner list state and retained aggregate; never claim deletion success before confirmation.
- **Bulk actions:** disable duplicate submit while processing. Display per-item completed/failed outcomes. A definitive rejection does not roll back other completed items; retry excludes confirmed successes. An unresolved operation is reconciled before any subsequent item is submitted. Query/cache invalidation occurs only after confirmed or reconciled persistence.
- **Archived write attempts:** the trusted functions reject archived parent lists even for direct RPC calls; reads stay owner-scoped. Session expiry and cross-user requests create no mutations.
- **Lock order:** owner profile lock for list count operations, then list lock, then dependent concepts/rounds/practices/notes, matching create and VS-03/VS-05 parent-first conventions. Verify with two-owner and concurrent synthetic requests; do not introduce a reverse lock path.

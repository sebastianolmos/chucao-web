## Proposed changes by component

### 1. Supabase migration and trusted data boundary

**Proposed path:** `supabase/migrations/<timestamp>_vs02_concept_management.sql`

Add a `public.concepts` resource linked to `public.lists`:

- `id uuid` stable identity, generated by the database.
- `list_id uuid` required foreign key to `public.lists(id)`.
- `title text` nullable only for a deleted row; active values are required,
  trimmed, and 1–50 characters.
- `description text` nullable only for a deleted row; active values are stored
  as trimmed text, empty when absent, and no more than 2,000 characters.
- `state text` constrained to the planned `pending` and `seen` values, with
  new records initialized to `pending`; VS-02 does not expose transitions.
- `position bigint` assigned in insertion order within a list.
- `created_at timestamptz` and `updated_at timestamptz`.
- `deleted_at timestamptz null` as the logical deletion marker.

On logical deletion, the trusted operation shall set `deleted_at` and clear
`title` and `description`. The remaining row is the minimum tombstone
reference (`id`, `list_id`, state, position, timestamps, and deletion marker);
future historical views can render `Deleted concept` without retaining active
user-authored content in the concept row.

Add constraints and indexes:

- Trim and length checks for title and description.
- A partial unique index on `(list_id, title)` for active rows
  (`deleted_at is null`) using exact case-sensitive equality.
- An index supporting active concept reads by `(list_id, position, id)`.
- An index supporting ownership resolution through `list_id` if the query
  planner needs it after migration review.

Add deny-by-default RLS:

- Active reads require that the related list has `owner_id = auth.uid()`.
- Direct anonymous and cross-user reads/writes/deletes are rejected.
- Direct table writes are not the public client contract; grant only the
  minimum read/execute privileges needed by the chosen operations.
- Logical deletion remains subject to ownership checks and is never exposed
  through the active collection query.

Use trusted SQL functions for operations whose correctness depends on
validation, ownership, ordering, or compare-and-swap behavior:

- Create one concept.
- Create a reviewed batch atomically.
- Update title/description with an expected `updated_at`.
- Mark a concept logically deleted with an expected `updated_at`.

Each function shall derive the owner from `auth.uid()`, verify the list
relationship, validate all limits, use fixed SQL and bound values, set
`search_path` explicitly, and return domain-safe error messages/codes. The
exact SQL signatures belong in the implementation task and typed contract;
they must not accept a client-supplied owner or bypass RLS intent.

### 2. Database types and service contract

**Existing path:** `src/lib/database.types.ts`  
**Proposed path:** `src/features/concepts/conceptService.ts`

Add `ConceptRow` and database table/function types. Keep the public service
contract independent from Supabase error shapes:

```text
ConceptRow:
  id, list_id, title?, description?, state, position,
  created_at, updated_at, deleted_at

BatchCandidate:
  sourceIndex, title, description

BatchOmission:
  sourceIndex, rawLine, reasonCode

BatchReview:
  accepted: BatchCandidate[]
  omitted: BatchOmission[]
  rawInput
```

The service shall expose operations equivalent to:

- `getOwnedConcepts(userId, listId)`: assert the current user, select active
  concepts ordered by `position` then `id`, and map service failures.
- `createConcept(input)`: validate locally, call the trusted create operation,
  and return the persisted row only after confirmation.
- `createConceptBatch(review)`: send only reviewed accepted candidates, use
  one trusted atomic operation, and return persisted rows plus a result
  summary.
- `updateConcept(input, expectedUpdatedAt)`: call compare-and-swap update and
  map stale updates to a conflict error.
- `deleteConcept(id, expectedUpdatedAt)`: call logical deletion and map
  uncertain/failure outcomes without fabricating success.

All service operations shall verify the current Auth UUID before using a
`userId` supplied by a view, following `listService.ts`. Query keys shall
include the authenticated user and list identity so account changes cannot
reuse another account's data.

### 3. Pure batch parser and validation

**Proposed path:** `src/features/concepts/conceptParser.ts`

Keep parsing and deterministic validation separate from network operations:

1. Reject raw input above 20,000 characters including line breaks or above
   100 lines before producing a confirmation review.
2. Split on line boundaries while preserving source indexes and original text.
3. Accept candidates whose trimmed line begins with one `-`; remove that
   marker and trim the remainder.
4. Split the remainder at the first `:` when present. The left side is the
   title and the right side is the description; later colons remain part of
   the description.
5. Trim title and description, then apply the 1–50/2,000 limits.
6. Reject empty, malformed, over-limit, and exact case-sensitive duplicate
   titles with stable reason codes.
7. Preserve the first valid occurrence in input order and omit later
   duplicates.

The parser shall return no persisted side effect. The database function shall
repeat all security-relevant validation and duplicate checks because browser
validation is advisory.

## Data model, contracts, and compatibility

### Ownership and visibility

The ownership chain is `concepts.list_id -> lists.id -> lists.owner_id ->
auth.uid()`. The client never supplies an owner identity accepted by the
database. Active queries filter `deleted_at is null`; deleted rows are not
returned to active list or detail views.

The logical deletion marker preserves stable identity and minimum relationship
data for future historical references. The delete operation clears the
concept-row title and description, so active or future tombstone reads cannot
expose that content. Later history slices may store title snapshots for
appearances independently of this tombstone.

### Ordering and batch atomicity

`position` is the authoritative incorporation order for this slice and later
concept ordering. The trusted batch operation shall lock the list scope,
allocate a contiguous position range, and insert accepted candidates in input
order. A failed batch transaction creates no accepted rows. This prevents
partial confirmation and makes reload ordering deterministic.

If a request times out after the database commits, the client shall reconcile
by re-reading active concepts and matching the accepted titles/descriptions
exactly. It may show the persisted result when every accepted item is found;
otherwise it shall show an unresolved state and must not blindly resubmit.
Unique active-title enforcement prevents duplicate active records.

### Edit concurrency

The service sends the last confirmed `updated_at` with an edit or delete.
The trusted operation updates only when that value still matches. A zero-row
compare-and-swap result maps to `concept_conflict`; the UI keeps the newer
server value authoritative and offers `Reload current version`.

### Proposed service error contract

The shared domain error mapping shall recognize stable codes equivalent to:

| Code | User-visible meaning | No-write/no-change guarantee |
|---|---|---|
| `concept_title_invalid` | Title is empty or outside 1–50 characters | No concept mutation |
| `concept_description_invalid` | Description exceeds 2,000 characters | No concept mutation |
| `concept_duplicate` | Exact active title already exists in the list | Existing concept remains unchanged |
| `batch_limit_exceeded` | Input exceeds 100 lines or 20,000 characters | No batch mutation |
| `concept_conflict` | The saved version is stale | Newer server value remains unchanged |
| `concept_not_found` | The active concept is unavailable | No fabricated success |
| `unauthenticated` / `unauthorized` | Session or ownership is invalid | Protected data is not disclosed |
| `unavailable` / `unresolved` | Service result cannot be confirmed | Retry/reconciliation required |

Internal SQL text, IDs belonging to another user, credentials, and raw
user-authored content shall not be placed in localized error messages or
diagnostic output.

### Compatibility and migration

The new migration must be additive and apply after the VS-01 migration. It
must not rewrite existing profile/list rows. A local database reset shall
recreate both migrations in order. Existing VS-01 clients that only read
lists remain compatible; the minimal List Detail empty message is intentionally
replaced by the VS-02 concept surface.

No backfill is required because no concept data exists in the current
repository snapshot. If the migration encounters an existing development
database with manually created concept-like data, it must not guess a
transformation; reset or an explicitly reviewed migration path is required.

## Algorithms and failure handling

### Individual create

```text
validate and trim title/description locally
if invalid: keep form values and show field error
call trusted create operation with list_id and values
if confirmed: invalidate/reload concepts and show success
if duplicate/validation: keep form and show mapped error
if unavailable/uncertain: reconcile active concepts before offering retry
```

The trusted operation repeats validation, checks list ownership, allocates
the next position, and inserts one active row in one transaction.

### Batch create

```text
review = parseAndValidate(rawInput, existing active titles)
show accepted and omitted entries
on confirmation:
  send accepted candidates only
  trusted operation validates all candidates and inserts atomically
  on confirmed success: reload and show ordered result summary
  on failure: preserve review/raw input and show retryable error
  on uncertainty: reload and reconcile exact accepted values
```

The client must not issue one network mutation per accepted line. A duplicate
or validation conflict discovered at confirmation causes the operation to
return without partial inserts; the client refreshes current state and
rebuilds the review as needed.

### Edit and delete

- Edit submits the current row identity and `updated_at`; a conflict leaves
  the server version authoritative and does not reset the local form silently.
- Delete first requires explicit confirmation, then submits identity and
  `updated_at`. A confirmed operation sets the tombstone marker, clears the
  title/description, and removes the row from active query results.
- Timeout or transport failure never becomes an optimistic success. The
  service re-reads the active collection where possible and reports
  confirmed, unchanged, or unresolved state.

### Account changes and cache isolation

`App` already removes `lists` and `profile` queries when the Auth UUID
changes. Concept query keys must include the same user identity and list ID;
the concept view must unmount or clear local draft/review state when those
inputs change. No persisted draft or concept content is placed in browser
storage.

## Technical decisions and rationale

| Decision | Choice | Rationale and consequence |
|---|---|---|
| Trusted writes | Versioned Supabase SQL functions with RLS-backed ownership | Batch atomicity, server-side validation, and compare-and-swap cannot rely on browser sequencing. It follows ARCH-04/ARCH-05 and the existing VS-01 function pattern. |
| Active deletion | Logical deletion/tombstone | Preserves future historical references and safe retry while hiding deleted content from active views. Final erasure remains a later account/retention concern. |
| Edit concurrency | `updated_at` compare-and-swap | Reuses the existing timestamp/trigger pattern and rejects stale writes without automatic merge ambiguity. |
| Batch processing | Client review plus server revalidation and one atomic write | Gives immediate feedback without trusting the browser and prevents partial batch persistence. |
| Input boundary | 100 lines and 20,000 characters including line breaks | Confirmed product decision; bounds client work and service exposure without limiting ordinary personal use. |
| Ordering | Per-list monotonic `position` | Makes input/insertion order deterministic across reloads and supports later incorporation ordering. |
| New external dependency | None | Existing React, Mantine, React Hook Form, TanStack Query, i18next, Supabase, and CSS Modules cover the slice. |
| Parser delimiter | First `:` after the leading marker separates title from description | Preserves additional colons in descriptions and implements the confirmed `- Title : Description` form. If clarification later changes this observable rule, update the spec before implementation. |

### Rejected alternatives

- **Client-only validation and direct table writes:** rejected because SEC01,
  SEC04, and Q02 require trusted ownership, validation, and atomic effects.
- **Physical deletion of the concept row:** rejected because it would remove
  the stable reference needed by future historical behavior and complicate
  safe retry.
- **Automatic edit merge:** rejected because title/description changes are
  user-authored content and silent or ambiguous merging risks data loss.
- **One RPC call per pasted line:** rejected because it permits partial
  confirmation and makes retry/reconciliation harder.

### Risks and mitigations

| Risk | Mitigation | Verification point |
|---|---|---|
| RLS policy exposes concepts through a guessed list/concept ID | Test unauthenticated and cross-user direct reads/writes/deletes against the local service | CHECK-07 |
| Client and server parse/validation rules diverge | Keep parser reason codes stable and repeat every security-relevant rule in SQL | CHECK-02 and CHECK-07 |
| Timeout after commit creates duplicate concepts on retry | Atomic batch, active-title uniqueness, exact reconciliation before retry | CHECK-04 |
| Concurrent edit silently loses data | Timestamp compare-and-swap and explicit reload-current-version state | CHECK-05 |
| Tombstones leak deleted content | Active queries exclude deleted rows and responses omit title/description for deleted state | CHECK-06 and CHECK-07 |
| Large pasted input blocks the browser | Reject 100-line/20,000-character boundary before parsing and review bounded workloads | CHECK-02 and CHECK-08 |
| Account switch reuses private cache/draft | User/list query keys plus local-state reset on identity change | CHECK-07 |
| Long Spanish/English text clips or hides errors | Responsive review with long titles/descriptions and keyboard/touch checks | CHECK-09 |

### Open technical decisions

No product-behavior decisions remain open. The task breakdown may refine SQL
return shapes, exact migration timestamp/name, component decomposition, and
the existing repository's eventual test-runner choice without changing the
spec's observable behavior.

## 2. Context and objective

The application has locally validated private study journeys for accounts, lists, concepts, rounds, timed practice, notes/history, and advanced organization. VS-06.5 also provides the bilingual About page and a non-persistent guest timer preview. Local implementation does not show that the product can be reconstructed, configured, operated, or used accessibly and privately in the intended release environments.

VS-07 gives the release operator an evidence-based decision about whether the integrated product is ready for a later release. The user outcome is a production build served locally, backed by an isolated local Supabase environment and test data, whose setup, schema, configuration, privacy operations, and agreed PC/mobile-viewport journey can be reproduced and reviewed. Hosted staging and production publication are outside this slice; any later production release requires all applicable gates and separate release authorization.

This increment is a release-readiness slice, not another feature slice. Code changes are limited to defects or bounded configuration/documentation changes required to meet its acceptance criteria. Existing study behavior, localized content, and private-data boundaries remain in force.

## 3. Actors and preconditions

- **Release operator:** prepares the release candidate, follows the documented migration/deployment/recovery process, and records release-gate results.
- **Authenticated person:** exercises the integrated private study journey with an account they own.
- **Prospective registrant:** reaches Access and the applicable privacy information before any enabled public registration flow.
- **Provider or privacy reviewer:** supplies or reviews evidence for provider processing, transfers, retention, backup/recovery, applicable obligations, and public notices where required.

Before validation, VS-01–VS-06 must remain closed for their recorded local scopes; VS-06.5 behavior is present locally. Candidate checks use test accounts and content. The agreed scope is a locally served production build with local Supabase, stable Chrome on PC, and Chrome DevTools Device Toolbar for a mobile responsive viewport; public Google registration is for a later launch. Physical Android compatibility is not claimed. External provider evidence, responsible contacts, and provider backup-retention facts remain conditions for any future public launch; see OQ-04, OQ-05, and OQ-07.

## 4. Scope and exclusions

### Included

- Define the evaluated PC Chrome and mobile responsive viewport and verify the integrated Spanish/English journey in those browser dimensions; physical Android compatibility is not part of this local evaluation.
- Reproduce a clean setup, apply the versioned database migrations to isolated local Supabase, create and serve the production client build locally, and exercise the local candidate using synthetic data. Hosted staging and production deployment are excluded.
- Validate the authenticated product journey and VS-06.5 guest About/timer behavior, including localization, accessibility, route behavior, ownership, error/recovery states, and preservation of existing data rules.
- Implement the bounded Chucao account lifecycle needed for launch in VIEW-11/FLOW-08: show Google identity, distinguish sign-out from deletion, require explicit confirmation, delete the Chucao account and its active personal data, end the session, and return to Access. The Google account remains intact; no unrelated account features are added.
- Review the locally built client artifact and repository-controlled configuration for secrets, debug/test assets, dependencies, routing, and environment separation. Record hosted HTTPS, headers, and provider configuration as future launch checks; this slice does not inspect a deployed artifact or live hosting configuration.
- Verify actual data flows and provider evidence; browser/runtime auxiliary disclosure; the privacy information already prepared in the app and any necessary corrections to match observed behavior; registration/session lifecycle; rights and incident procedures; retention, deletion, backup, and restoration handling. Keep only a minimal private release record of evidence and blockers; prepare it during release work, not as a new app feature or a documentation project now.
- Record a release decision with evidence and explicit blockers. Production publication is gated by all applicable checks and the release authorization defined during clarification.
- Make only bounded fixes needed to pass these release criteria; retain the established Chucao visual and interaction system.

### Excluded

- New study, sharing, analytics, marketing, import/export, public indexing, active-session synchronization, or unrelated account features such as password creation/recovery.
- Changes to list, concept, round, practice, note, history, archive, or guest-preview semantics except a bounded fix needed for a release criterion.
- A new design system or redesign of existing views; preserve the implemented flow and styling.
- Claiming legal compliance, provider certification, anonymity, or suitability for jurisdictions not reviewed by the responsible human reviewer.
- Processing real-user data before the applicable privacy, provider, security, and operational gates are resolved.

## 5. Scenarios

### SC-01 — Reconstruct and prepare a release candidate

Given a clean source checkout, local Supabase, synthetic data, and local environment configuration, the release operator follows documented setup, applies all versioned migrations to an empty local database, creates the production build, and serves it locally. The operator can reach the app and its nested routes, and the candidate reports usable success/failure states. A setup, migration, build, or serving failure is recorded; it is not bypassed by modifying production data manually. Hosted staging and production deployment are not part of this scenario.

### SC-02 — Complete the integrated journey on supported devices

Using owner A on the evaluated PC Chrome and mobile responsive viewport, exercise Google/Supabase authentication, list and concept organization, a study round, associated and independent timed practice, explicit practice save with optional note/rating, history, locale change, About, and sign-out. Also exercise the signed-out Access → guest timer → return journey and verify that it creates no practice, note, or history record. With test owner B, verify owner A's private resources remain inaccessible through the direct service boundary. Representative network/session failure and recovery must not report false success, lose an accepted save, or expose another user's data. Device Toolbar tests responsive presentation and does not establish Android-device compatibility.

### SC-03 — Evaluate publication and operational gates

The release operator reviews the candidate artifact/configuration, accessibility/browser evidence, actual data-flow and provider evidence, privacy notice/collection point, rights and incident process, retention/deletion rules, and a controlled backup restoration. If any required evidence is missing or a material decision remains unresolved, the candidate stays unpublished for real users and the blocker, evidence owner, and next decision are recorded.

### SC-04 — Delete a disposable Chucao account

Given a disposable synthetic owner with private records and a second synthetic account, the owner opens Account and requests Chucao account deletion. Cancelling leaves the account and its data unchanged. Confirming deletion removes the Chucao account and its active personal data, ends the Chucao session, and returns to Access; the Google account itself remains intact. While deletion is pending or partially failed, access to Chucao data is blocked, completion is reported as unconfirmed, and safe retry/support is available. Provider-managed backup retention remains a pre-public-launch dependency under OQ-07. A failure or uncertain result does not alter the second owner's resources.

## 6. Functional requirements

### Release setup and user journey

- **FR-01 — Evaluated targets (Q03, Q05):** Evaluate stable Chrome on PC and a mobile responsive viewport using Chrome DevTools Device Toolbar. Record the exact PC Chrome/OS and the emulated viewport when its preset/dimensions are available; identify them as not captured otherwise. The integrated journey shall be operable at both evaluated dimensions; viewport emulation is not Android compatibility evidence and this slice makes no physical Android support claim.
- **FR-02 — Reproducible setup and schema (Q05, Q02):** The release operator shall be able to follow documented clean setup and apply the repository's versioned migrations to an empty, isolated database without manual schema edits. A failed or partially applied migration shall be visible, and production promotion shall stop until a safe resolution/recovery path is documented and exercised in non-production.
- **FR-03 — Environment isolation and candidate delivery (Q05, SEC10, DP12, DP19):** The local candidate shall use isolated local Supabase services, synthetic data, and only public browser credentials. Its setup shall not connect to or mutate production services/data. Hosted staging and production configuration/deployment are outside VS-07 and require separate authorization if pursued later.
- **FR-04 — Integrated product journey (Q01, Q03, Q06):** At each agreed browser dimension, an authenticated person shall be able to complete the existing private journey: create/manage a list and concepts, draw/mark within a round, use the timer, explicitly save an eligible completed practice with optional note/rating, and review history. Existing list/concept organization and archive rules remain unchanged. The visitor shall also be able to read About and preview the guest timer; the guest preview remains transient and cannot save or create history. Spanish and English shall remain available, and changing locale shall preserve the current safe destination and unsaved values where current behavior requires it.
- **FR-05 — Authentication and registration exposure (SEC05–SEC07, DP09, DP11):** Google/Supabase Auth shall continue to own the authentication/session flow; the release shall use the confirmed account lifecycle and session behavior without application-managed passwords or recovery bypass. The eventual launch shall allow any person to register with Google. Public registration shall remain closed until provider settings, abuse controls, privacy notice, and recovery/session behavior are reviewed and the applicable release gates pass. This launch decision does not enable registration during VS-07 local verification.
- **FR-06 — Routes and page identity (WEB02, WEB03):** Direct entry, refresh, deep links, and unknown routes shall behave usefully under the agreed hosting/routing configuration. Every released route shall have a meaningful localized title, heading, language metadata, and semantics; the favicon and language changes shall be correct in Spanish and English.
- **FR-17 — Chucao account lifecycle (CAP-01, SEC04, SEC05, DP11, DP14–DP16, DP18):** The release shall provide the bounded Account behavior: show available Google identity, distinguish Chucao sign-out from account deletion, and offer explicit deletion confirmation that explains affected Chucao data. Cancel shall leave identity/session/data unchanged. On confirmed deletion, the Chucao account and its active personal data shall be removed, the Chucao session shall end, and the user shall return to Access; the underlying Google account shall not be deleted. Rounds still linked to the account's lists shall be deleted before account cascades run; this action shall not create anonymous round totals. Anonymous aggregate round totals detached by prior permanent list deletion shall be retained without an owner link, consistent with the existing list-deletion rule. While deletion is pending or partially failed, the account shall be blocked from accessing Chucao data; the interface shall explain that completion is unconfirmed and provide a safe retry or support path. Retries shall be safe and shall not restore or duplicate data. Provider-managed backup retention remains subject to OQ-07.

### Accessibility, privacy, and release controls

- **FR-07 — Accessibility and visual/flow continuity (Q03, WEB03, WEB04):** Representative journeys shall support keyboard operation, visible focus, accessible names/labels, understandable errors, zoom, reduced motion, touch/viewport use, and screen-reader interpretation of the Chucao scene and controls. The implementation shall preserve the current Chucao composition and interaction patterns: cream/panel surfaces, coffee-brown borders and offset shadows, Comfortaa typography, responsive layouts, Access actions (cyan Google, lilac guest timer, light-orange selected locale), and About immediately before History in authenticated navigation. Color alone shall not communicate selection or state. A bounded accessibility fix may adjust a control while retaining the established visual system.
- **FR-08 — Trusted ownership and safe rendering (SEC01–SEC04, DP10):** Every released list, concept, round, practice, note, history, and preference operation shall continue to enforce the authenticated Supabase UUID ownership boundary. Unauthorized and cross-owner direct reads/writes/deletes shall be rejected without data change or disclosure. Existing validation and text rendering protections shall remain effective for user-authored content.
- **FR-09 — Actual data flows and auxiliary disclosure (DP02, DP03, DP13, DP19):** Before release, the data inventory shall match observed browser requests/storage, service requests/responses, URLs, browser history/cache, logs/diagnostics, provider flows, and backups. Credentials and unnecessary user-authored/private data shall not be exposed through errors, URLs, diagnostics, or unrestricted copies. Evidence shall use synthetic accounts/content and contain no unnecessary personal data. Existing VS-05 MV-02 browser runtime inspection is an explicit pending item and shall be completed here.
- **FR-10 — Privacy information and collection notice (DP08, DP09):** Reuse the privacy information and prepared text already present in the app; do not create a second notice or separate privacy feature. Before public registration or other data collection, verify that the existing information is reachable without an account, understandable, and accurate to observed data, purposes, providers/recipients, applicable transfers, retention, rights/contact, policy version/date, and other applicable disclosures. Make only corrections needed for accuracy and completeness. Any concise notice/link required at the Google registration collection point shall use this existing information. Public contact destinations and final applicability review remain under OQ-04/OQ-05.
- **FR-11 — Provider, transfer, and registration review (DP01, DP05, SEC05–SEC07):** Before real-user processing, the release record shall identify the controller/responsible contact and document Google, Supabase, and Cloudflare data sent, roles, locations, subprocessors, retention, deletion/return, incident terms, and applicable transfer safeguards. Provider evidence and its owner/source remain OQ-04. Conditional criteria DP04/DP06/DP07/DP20 remain out of scope unless the actual audience or processing activates them; such activation requires a separate review before use.
- **FR-12 — Retention, rights, and account lifecycle (DP11, DP14–DP17):** Account/session behavior, content retention, account/list deletion, correction, applicable access/export, objection, and restriction handling shall match the documented policy and actual provider behavior. A workable manual rights process may be used if permitted, but it shall identify the public contact, ownership verification, tracking, secure response, and applicable time/exception handling. The operator shall verify a synthetic request and ensure a restriction/deletion is not undone by ordinary operation or restoration.
- **FR-13 — Backup and recovery (Q05, DP12, DP14, DP18):** Before real-user use, the operator shall document actual backup retention/access and exercise restoration in an isolated environment. Recovery shall reapply applicable deletion/restriction states before restored records return to normal use and shall not silently reactivate accounts, permissions, or prohibited processing. While account deletion is pending or partially failed, restoration shall not make that account or its data available. A code rollback shall not be represented as a database rollback. Provider restoration facts and release recovery authority are part of OQ-04.
- **FR-14 — Incident response (DP21):** Before public operation, a named responsible person, detection/escalation contacts for the providers, containment/investigation/evidence/recovery steps, and a method for deciding notifications under applicable rules shall be documented. A proportionate synthetic exercise shall show the contact and response path is usable.
- **FR-15 — Artifact and configuration review (WEB08, SEC10, Q06):** The local production artifact and repository-controlled client configuration shall contain only intentionally public files/values; review shall find no privileged keys, unintended source maps/test/debug resources, unsafe checked-in settings, or unreviewed dependencies. Record HTTPS/certificate, headers, provider settings, redirect origins, and applicable cross-origin/state-change protections as pre-public-launch checks where they depend on hosted configuration; no live production configuration is claimed as verified by VS-07.
- **FR-16 — Release gate and hold (Q01, Q05, Q06, DP01–DP21 as applicable):** The release record shall map each applicable criterion to evidence and mark it met, pending, or not applicable with rationale. A required unresolved decision, failed gate, missing provider/recovery/privacy evidence, or unsupported target shall prevent opening public registration or using real-user data. Any exception requires an explicit human decision with rationale and scope; a plan, configuration, local test, or synthetic fixture alone shall not be described as production evidence.

## 7. Applicable non-functional requirements

- **NFR-01 — Preserve the implemented Chucao experience (Q01, Q03, Q06):** Release fixes shall follow the visual tokens, component treatments, responsive shell, navigation order, bilingual copy, and flow in `docs/design.md` and `docs/app-flow.md`. Do not introduce new feature journeys, generic redesigns, or test-only interface changes. The VS-06.5 About/guest-preview states are part of the current baseline; their no-save boundary must remain explicit.
- **NFR-02 — Accessibility and responsive compatibility (Q03, WEB02–WEB04):** Acceptance is evaluated on stable Chrome for PC and a mobile responsive viewport with representative keyboard, screen-reader, zoom, reduced-motion, touch, responsive, route, metadata, and image/control checks. Record the exact PC browser/OS and emulated viewport; this slice makes no physical Android or other untested browser/version support claim.
- **NFR-03 — Minimum sufficient verification (Q01–Q06, V01–V13):** Verification shall reuse existing automated coverage and add/modify automated tests only for materially changed, repeatable code behavior with a meaningful assertion. Do not create one test per requirement, add a broad end-to-end suite, or add tooling solely to mirror this spec. A small number of complete release-candidate workflows and targeted real-boundary/security/restore checks may be manual or integration checks where automation would not establish provider, visual, browser, or operational behavior. Exact test selection and commands belong in the technical plan.
- **NFR-04 — Representative workload and bounded resource use (Q04, SEC08):** The release shall retain usability for the agreed representative personal data volume: one synthetic account with 10 lists, up to 50 concepts per list, and 200 practice-history entries. Exercise search/organization, concept filtering/detail, history, and timer interactions at this volume. This is an evaluation fixture, not a product limit or a latency promise. Record observed issues and environment; do not invent a numeric performance threshold. Q04/SEC08 review shall also consider relevant service quotas and cost exposure.
- **NFR-05 — No unsupported legal or operational claim (DP01–DP21):** Public-facing statements and release records shall distinguish local evidence, provider evidence, human legal review, and unresolved assumptions. The spec or engineering checks shall not claim general legal compliance, anonymity, or immediate backup erasure without evidence.

## 8. Errors, boundaries, and preservation

- A clean install, migration, build, candidate deployment, backup restoration, or browser journey failure remains visible and actionable; the release cannot be marked ready by bypassing the failed step (FR-02, FR-03, FR-13, FR-16).
- An unavailable provider, unknown retention period, missing public contact, or unresolved launch registration decision remains a named blocker to the affected real-user/publication gate; it is not replaced by an assumed value (FR-05, FR-10–FR-14, FR-16).
- Auth cancellation/session expiry returns to the documented safe state and permits retry; signed-out users remain out of private data. A/B direct cross-owner requests cause no data change or disclosure (FR-05, FR-08).
- Cancelling Chucao account deletion changes nothing; a pending/partially failed deletion blocks access to Chucao data, reports unconfirmed completion, and offers safe retry/support; retries do not restore or duplicate data. A confirmed deletion removes the Chucao account and its active personal data, cannot leave that account signed in, and does not affect another owner's resources (FR-17).
- A migration/data restore failure or a restored deletion/restriction mismatch shall keep the candidate isolated; do not promote or process real-user data until recovered and rechecked. Restoration reapplies pending/completed deletion states before restored records can be used (FR-02, FR-13, FR-16, FR-17).
- The guest timer remains transient, and the About page remains available in both locales with the Access/authenticated content distinction (FR-04, FR-07).
- Existing list/concept/round/practice/note/history rules and successful local flows remain unchanged except for bounded, separately evidenced fixes needed to meet this release spec (FR-04, FR-08, NFR-01).

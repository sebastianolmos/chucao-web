- `src/lib/supabase.ts` creates the browser Supabase client with the publishable key, PKCE, persistent sessions, and token refresh. It has no privileged credential and must remain that way.

A user-authenticated Edge Function can use a verified JWT, while its server-side environment can hold a privileged key; local function secrets are read from `supabase/functions/.env` and production secrets are configured separately ([Securing Edge Functions](https://supabase.com/docs/guides/functions/auth), [Edge Function secrets](https://supabase.com/docs/guides/functions/secrets), reviewed 2026-11-19).

Supabase's CLI documents `db reset --local` as recreating the local database and replaying migrations; never use a remote reset for this plan ([`supabase db reset`](https://supabase.com/docs/reference/cli/supabase-db-reset), reviewed 2026-11-19).
- `package.json` provides `npm run build` (`tsc -b && vite build`), `npm run lint` (`oxlint`), `npm test` (`vitest run`), and `npm run preview`. ### Account deletion sequence

```mermaid
sequenceDiagram
    actor Person
    participant UI as Account view
    participant Edge as Supabase delete-account function
    participant DB as PostgreSQL/RLS
    participant Auth as Supabase Auth admin
    Person->>UI: Confirm Chucao account deletion
    UI->>Edge: Invoke with current user JWT; no target UUID
    Edge->>DB: Begin idempotent deletion; mark pending
    DB-->>Edge: Pending state committed; private access now denied
    Edge->>DB: Remove still-linked rounds before list cascades
    Edge->>Auth: Delete the authenticated Auth UUID (server secret)
    alt Auth deletion confirmed
        Auth-->>Edge: Deleted
        Edge->>DB: Mark request completed
        Edge-->>UI: Completed
        UI->>UI: Local sign-out, clear caches, return to Access
    else Failure or uncertain result
        Edge-->>UI: Pending/unconfirmed; retryable
        UI->>UI: Keep private views blocked; show retry/support
    end
```

The marker and all account-owned data transitions must be serialized per Auth UUID. A retry may repeat cleanup and Auth deletion safely; it must not reopen private access, recreate the profile, or create anonymous round totals. After a successful deletion, the marker remains outside any old restorable snapshot for the period determined by OQ-07. This is a minimal privacy-sensitive operational record and is not exposed in the app or public repository.

## 4. Data model, contracts, and compatibility

### Proposed lifecycle contract

The migration should introduce a narrowly scoped `public.account_deletion_requests` record, keyed by the stable Auth UUID and not FK-cascaded with `auth.users`, so pending/completed deletion decisions can survive account deletion and be reapplied during recovery. Proposed columns are `user_id uuid primary key`, `state text check (state in ('pending','completed'))`, `requested_at timestamptz not null`, and nullable `completed_at timestamptz`. Do not store email, display name, list content, or a free-text deletion reason. Enable RLS, revoke browser-role table access, and permit state mutation only through tightly scoped `SECURITY DEFINER` functions/Edge Function authority. Keep the service role out of SQL callable from the browser.

The caller-facing status operation derives `user_id` only from `auth.uid()` and returns `active` or `deletion_pending`; it does not expose a deletion ledger or other account's state. The begin-deletion operation accepts no user identifier, locks/creates the caller's marker idempotently, transitions `active → pending`, and removes linked rounds before list deletion cascades. Deletion is a terminal transition to `completed`; there is no transition back to `active`. A pending account may invoke only lifecycle status/retry and sign-out, not ordinary list, round, practice, note, history, preference, or profile operations.

The Edge Function request contains no target account identifier. Missing/invalid JWT returns unauthorized; a valid caller can affect only their own Auth UUID. Successful Auth deletion cascades remaining profile/list/concept/practice/note data using existing FK relations. Any returned/uncertain Auth error is reconciled against the same user: confirmed absence completes the deletion; confirmed presence preserves pending state and a retry path; inconclusive state stays pending and never reports success. Repeated calls return the current terminal/pending state without reactivating data. The exact HTTP status/error envelope is an implementation contract to be finalized in tasks, provided these observable states remain stable.

### Round history and account deletion

The existing permanent-list-delete trigger in `20261120140000_vs05_anonymize_rounds_on_list_delete.sql` detaches rounds and stores anonymous totals. Current schema gives detached rounds no owner/list link. Account deletion therefore removes rounds still linked through the account's lists before cascades, preventing new anonymous totals for that account. Totals detached by earlier list deletion cannot be attributed back to an owner and remain under the existing anonymous-history rule. The UI/privacy copy must not imply that these already-anonymous totals are tied to or recoverable for a deleted account.

### Restore behavior and retained state

Deletion markers needed to reconcile a pre-deletion backup must be retained outside the snapshot being restored. The operator's restricted recovery manifest contains only the Auth UUID and pending/completed state/time, no email or authored data; restore tooling reapplies it before opening the restored environment to ordinary use. Keep this manifest only until every backup capable of restoring the deleted account has expired, then remove it. Provider expiry/access evidence is OQ-07 and blocks public launch, not the local implementation plan. A local recovery fixture proves the sequence, not provider backup behavior.

No existing client consumer receives a new database table or elevated capability. Existing `profiles`, list/concept/history contracts, and Auth ownership remain stable for active users. Existing anonymous list-history behavior remains unchanged. Additive migrations only; never edit already-applied migrations. Do not claim that code rollback undoes the account deletion or schema migration.

## 5. Algorithms and failure handling

1. **Confirmation and client lock:** Account view explains affected Chucao data and distinguishes Chucao deletion from Google-account deletion. Cancel closes confirmation with no service call or state change. On confirmation, immediately enter an in-memory locked/pending view and disable navigation/data queries while the backend establishes durable pending state.
2. **Durable pending state:** Edge Function verifies the Supabase user JWT and derives the Auth UUID. A caller-bound transaction writes/locks the pending marker before destructive cleanup. RLS policies and every exposed `SECURITY DEFINER` operation consult the shared active-account predicate. The same transaction removes still-linked round rows before user/list cascades could anonymize them. No other user's data is addressed.
3. **Auth deletion:** Server-side admin operation deletes only the caller UUID. The browser never receives a service-role/secret key. Handle returned errors and transport uncertainty as pending unless an authoritative same-user lookup confirms deletion. The function is safe to call again while the Auth user exists; pending status is never cleared by a retry failure.
4. **Completion:** After confirmed Auth absence, mark the non-cascading marker `completed`, return a completed result, then the browser locally signs out, clears `queryClient` data and in-memory practice state, and routes to Access. A lost response is reconciled on the next status/retry path; it must not restore content.
5. **Pending recovery:** A still-valid session that returns with a pending marker enters only the Account recovery state before `ensureProfile()` or locale/profile synchronization. The view offers retry and, once configured for future public operation, the existing privacy/contact route. No list, practice, History, or preference query can run while pending. If Auth has already been deleted, no user session is returned; do not recreate it just to display success.
6. **Restore:** Keep candidate isolated. Restore the approved local fixture, replay the restricted deletion manifest and any pending states, verify account/content access remains blocked, then perform ordinary validation. If manifest replay or state reconciliation fails, keep the restored candidate unavailable; never silently reactivate an account.
7. **Failure feedback:** Provider/network failures preserve the pending marker, identify that completion is unconfirmed, and offer retry. Do not display success, discard the pending recovery path, or tell the user their account is active if the backend state is uncertain. Support/contact details that depend on public operational setup remain pre-launch dependencies.

The current implementation creates user profiles automatically on session synchronization, so the order of operations matters: lifecycle status must be checked before `ensureProfile()` and the database function must refuse profile recreation for a pending marker. This protects direct requests and reloads, not only a hidden React button.
